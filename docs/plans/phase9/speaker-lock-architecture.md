# Phase 9: Speaker Lock (pVAD) Architecture Guide

**Status:** Deferred (Pending Future Implementation)
**Context:** This document captures the architectural decisions and context regarding the "Speaker Lock" feature (Personalized VAD). This was scoped out of the initial `nnnoiseless` integration to keep the PR focused, but the blueprint is recorded here for future coding agents.

## Goal
Implement a Speaker Verification (SV) gate that drops background speech (e.g., TVs, other people in the room) from triggering the downstream pipeline (STT -> LLM). 

**Scope:** While initially considered for the Tray only (since it's always-on), the user has clarified that Speaker Lock should apply to **ALL** interaction modes (Main App, Tray, PTT). If enabled, it is a global filter.

## The "Acoustic Mismatch" Problem

Background noise profiles affect speaker embeddings. If a user enrolls their voice in a quiet room, but is verified in a noisy room with the fan running, the SV model may reject them because the *acoustic profile* differs too much.

**The Solution:** The Speaker Verification engine must be positioned *after* the `nnnoiseless` denoiser in the pipeline. Enrollment audio MUST also pass through the exact same `nnnoiseless` pipeline before the baseline embedding is generated. 

## Model Choice: CAM++
We rejected ECAPA-TDNN (~85MB) due to the 8GB RAM / CPU-only baseline constraint. 
We selected **CAM++** (from Alibaba's 3D-Speaker project).
- Extremely lightweight (INT8 quantized ONNX is ~15-25MB).
- Fast CPU inference times.
- Highly accurate for short utterances (1-3 seconds).

**Action Required for Implementation:**
There are no official pre-exported ONNX weights for CAM++ in the Vox repo yet. The original Alibaba weights are PyTorch. Before writing the Rust code, a Python script (`scripts/export_cam_plus_plus.py`) using `funasr` or `speechbrain` must be written to export the model to ONNX format with dynamic axes for variable-length audio.

## Crate Selection: `simsimd`
To compare the 512-dimension f32 vector generated by CAM++ against the enrolled profile, we need to compute Cosine Similarity.
We will use the **`simsimd`** Rust crate (`simsimd = "6"`).
- It provides AVX2/NEON hardware-accelerated vector distance functions.
- It is significantly faster and more efficient than calculating it manually or pulling in a heavier math library.

## Threading & Concurrency Model

**Constraint:** The VAD actor runs on a Tier-2 prioritized thread (`ThreadPriority::Max` or 80). It processes 16ms audio chunks continuously. It **must not block** to run a 30ms ONNX inference.

**Architecture:**
1. **Dedicated SV Worker:** Create `app/src-tauri/src/services/audio/sv_worker.rs`. This will be a dedicated OS thread (not a tokio task, to avoid async overhead for pure math).
2. **The Hand-off:** When the `EarshotVadEngine` detects `SpeechEnd` and the VAD actor finalizes the `utterance_buffer`, it normally sends it to the STT engine. If Speaker Lock is enabled, it instead sends the `utterance_buffer` via `crossbeam_channel` to the SV worker.
3. **The Verification:** The SV worker runs CAM++ inference on the utterance buffer, extracts the embedding, and compares it to the enrolled profile using `simsimd`.
4. **The Gate:** 
   - If match (`simsimd::f32::cosine() >= threshold`): The SV worker forwards the buffer to the STT worker.
   - If impostor (`< threshold`): The SV worker drops the buffer and potentially sends a `VoxEvent::Cancelled` back to the pipeline.

**Why this works:** The 30ms latency of CAM++ inference on the SV worker overlaps entirely with the 500ms latency of the Nemotron STT decode. There is net-zero latency cost added to the user's perception of the pipeline.

## Settings & State
The `VadSettings` struct (in `core/settings.rs`) will need:
```rust
pub speaker_lock_enabled: bool,      // default: false
pub speaker_lock_threshold: f32,     // default: 0.72
```
A new IPC command `enroll_speaker_profile` will be needed for the wizard/settings UI to capture 5 seconds of audio, pass it through `nnnoiseless` + `CAM++`, and save the baseline `Vec<f32>` embedding to disk.

## Test Harness
Before merging Speaker Lock, a test binary `bin/sv_bench.rs` must be written that:
1. Takes a noisy audio file with background human speech (e.g., `low-voice-call.mp3`).
2. Generates impostor clips.
3. Reports False Accept Rate (FAR) and False Reject Rate (FRR).
Pass criteria is FAR < 10% and FRR < 15%. Erring toward acceptance (False Accept) is better UX for a local assistant than silently ignoring the actual user (False Reject).

## Future Advanced Integrations: DFN3 & TSE (Target Speaker Extraction)

During the research phase for noisy environments, **DFN3** (DeepFilterNet3) and **TSE** (VoiceFilter/Target Speaker Extraction) were evaluated as potential solutions. 

**Decision:** Both were rejected for the default `v0.9.0` baseline because they violate the core constraint: **CPU-only inference under an 8GB RAM total system budget**.

### Hardware-Tiered Profiles (16GB+ RAM, >4 Cores)
These models should be kept for future integration but MUST be gated behind a hardware-tiering system. They should only be allowed to load and run if the system profile detects **>= 16GB RAM and > 4 CPU cores** (or a dedicated GPU/NPU).

### DFN3 (DeepFilterNet 3)
- **Use Case:** Advanced non-stationary noise suppression (e.g., keyboard clacks, sudden bangs, complex background sounds) where `nnnoiseless` (which handles stationary fan noise) falls short.
- **Why Deferred:** DFN3 requires a stateful GRU which has a much higher CPU cost and memory footprint than the simple RNNoise port.
- **Implementation Note:** Like `nnnoiseless`, DFN3's hidden state must be explicitly zeroed out on session pauses/resumes to prevent state poisoning.

### TSE (Target Speaker Extraction)
- **Use Case:** Isolating the primary speaker's voice from other people talking in the same room. It essentially acts as a denoiser where the "noise" is other human voices, using a speaker embedding as the target condition.
- **Why Deferred:** Extremely computationally expensive. Running a TSE model continuously on the VAD hot path would blow the latency budget (sub-500ms pipeline) on a baseline 4-core CPU.
- **Implementation Note:** When implemented for 16GB profiles, it should likely run on a dedicated worker thread, potentially replacing the CAM++ SV gate entirely (since TSE inherently filters out the impostor voices before they hit the STT engine).

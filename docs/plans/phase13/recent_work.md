## Past Work (2026-10-11)

- **First full on-device onboarding run — Phase 4 moved from partial to BLOCKED.** The wizard now completes on hardware (POCO `22101320I` / Android 14): install, launch, manifest fetch, permission request, a **667 MB** STT download confirmed on disk, and completion. Running it end-to-end exposed **seven defects**, catalogued with root causes and `file:line` citations in [`android-device-defect-fixes.md`](file:///home/addy/projects/apps/vox/docs/plans/phase13/android-device-defect-fixes.md). Nothing in that plan is implemented yet.
- **⛔ Self-inflicted blocker — `ndk-context` is never initialized (D1, CRITICAL).** Twelve on-device panics: `ndk_context::android_context()` is `unsafe { ANDROID_CONTEXT.expect("android context was not initialized") }`, and nothing calls `initialize_android_context`; **`ndk-glue` is absent from both `Cargo.toml` and `Cargo.lock`**. Reached transitively via cpal during `AudioStream::new` (`core/engine.rs:300` → `services/audio/device.rs:114` → `cpal/host/oboe/mod.rs:288` → `android_media.rs:18`), because Oboe's `default_input_device()` returns an unconditional `Some(Device(None))` that brute-forces JNI config probes. **The Android `ndk-context` dependency and both its call sites were added by Phase 13 work in `2d10246e`, whose `SAFETY` comments assert an initializer that does not exist.** The assertion survived a clean dual-target compile because cargo cannot check it. Lesson recorded as an ordering rule: *verify a `SAFETY` claim about initialization order against `Cargo.lock`, not against intuition.*
- **Engage presents as an unkillable spinner, not a crash (D1 downstream).** Tauri drops the `OwnedInvokeResponder` when a command unwinds, so the JS `invoke()` promise **never settles** — no rejection, no timeout. `Home.tsx` disables its only control on `isLaunching` and renders Disengage only when `isEngaged`, which the pre-panic state never reaches. Release uses `panic = "unwind"`, so the process survives. **Generalised as Pitfall 19:** any backend panic becomes a silent frontend hang, so the frontend must bound its own IPC calls.
- **Notification permission is ungrantable and the UI concealed it (D2).** Device proof: `RECORD_AUDIO: granted=true`, `POST_NOTIFICATIONS: granted=false`. Backend logcat: `Permission request failed: lateinit property requestPermissionsLauncher has not been initialized` — `tauri-plugin-notification` 2.4.0's launcher is not registered in this Tauri setup, so **no notification dialog can ever appear**. Frontend then mapped the failure to `'unavailable'`, which `MobilePermissionStep.tsx:39` counted as **granted**, rendering a green tick. That contradicts the file's own contract in `setupService.ts:140-147` (*"Never render a bridge fault as a refusal"*) — here it renders as a **grant**. User-selected fix: register the missing launcher, keeping the plugin pinned at `=2.4.0`.
- **The mobile model step reported success it never achieved (D5).** The backend genuinely downloaded 667 MB; the UI lied three ways: `isDone` was set on the **first** `completed` event rather than all selected models (model 1 is 644 KB and finishes in <1 s — the desktop equivalent uses `.every(...)`); `Failed` events were discarded entirely; and any IPC error ran a **fake 20 %-per-600 ms timer to 100 %** (`MobileModelStep.tsx:168-178`), rendering failure as success. Also: category accordions summed **all** groups, ignoring `selectedIds` (`:133-136`), and `getRuntimeReport` raced `fetchManifest` in the same tick, making the pre-check dead on first run. Separately, `manager_ops.rs:191-195` aborts the whole batch on first failure, which stranded required models 12–13 — `models/embedding/` does not exist on device.

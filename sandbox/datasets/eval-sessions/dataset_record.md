# Vox Compaction + Memory Pipeline Eval Sessions

_Last Updated: 2026-10-09_

## 1. Purpose

Deterministic evaluation sessions for the production compaction, memory-ingestion, and personal-memory-consolidation seams.

The eval runs one shared database per case set. Cases are processed as normal sessions in sequence. Personal memory, episodic state, and consolidation state carry forward between cases within a run.

Evaluation judges are permitted and required: one LLM judge per layer (compaction, ingestion, consolidation), each returning strict schema-validated JSON. Every score in the run summary is a count produced by typed code from database state or a validated judge verdict. No figure is ever read out of judge prose. The judge never sees the session turns for compaction (baseline JSON vs runtime JSON only); it labels pre-enumerated decisions and near-misses for ingestion; it assigns observation coverage and audits operations for consolidation.

## 4. Execution Contract

- One shared database stores every case and all resulting state.
- Cases run sequentially as normal sessions.
- Each case starts at a different simulated time and is separated from the previous case by at least one day.
- Existing personal memory and consolidation state must not be reset between cases.
- Each case runs production budgeting, compaction, memory ingestion, and personal-memory consolidation in order.
- Evaluation runs production constructors, boundaries, and functions.
- Compaction runs in production-style slices: turns accumulate until the context budget reaches the critical threshold, the slice is compacted, and its session context becomes the next slice's prior summary. Slice boundaries are planned by the harness and dumped to disk before any generation so the reference baseline consumes identical ranges.
- The compaction reference baseline is generated by the same model with the same prompt and thinking enabled. The compaction judge compares baseline JSON to runtime JSON only.

### 4.1 Reference Baseline

The canonical baseline lives at `sandbox/datasets/eval-sessions/baselines/gemma4-12b/seed1` — 14 cases, 39 slices, 1041 facts.

| Property | Value |
|---|---|
| Backend | Local Ollama |
| Model | `gemma4:12b` |
| Seed | 1 |
| Temperature | **0.0** |
| Prompt source | `src/services/memory/compaction/prompt.rs` (read at generation time) |
| Output budget | 8192 (`num_predict`), except `case_12` at 16384 |

Three properties of this baseline are deliberate and must not be "corrected" without re-running the whole baseline:

- **Temperature 0.0, not the production 0.2.** A ruler that changes between runs cannot rank anything. Reproducibility was chosen over matching the production sampling temperature. Production remains at 0.2. The mismatch is surfaced in the run manifest, summary preamble, and `scorecard.json` via `baseline_meta`.
- **Case 12 uses `num_predict` 16384.** At 8192 it returned empty content on every seed: `think: true` consumed the entire output budget before any JSON was emitted. It is the only case generated at the larger budget, and its `_meta.json` records this.
- **Seed 1 was chosen from a two-seed comparison** (978 vs 977 facts over 37 shared slices — equivalent strength, not a lucky draw). Only the winning seed is retained.

Reproducibility was verified by generating the same slice twice at the same seed and diffing: byte-identical output.

A cloud baseline was attempted and rejected. NVIDIA NIM ignores both `temperature: 0` and `seed` for its mixture-of-experts models, returning materially different documents for identical input (40 vs 30 facts on one slice). It cannot serve as a fixed reference.

The harness reads only `<baseline_dir>/<case>/baseline/slice_NN.json`. The `slices/` inputs are not stored under `baselines/`; regenerate them with the harness `--dump-slices` flag if the baseline must be rebuilt.
- Ingestion is audited from the decisions it reports (stage, incoming fact, deactivated fact, measured similarity) plus near-miss pairs below threshold. The production summaries carry this telemetry; dedup behaviour itself is unchanged.
- Consolidation is audited from the resolved operations, their refusal reasons, and the resulting blocks with IDs. The eval runs `suggestion_policy = "auto_apply"` so deletions reach the committed state and are measurable; the production default `manual_review` stages them instead.
- The run must report missing records, failed stages, unexpected state resets, threshold mismatches, invalid cross-case memory continuity, and any judge response that failed schema validation (reported separately, never as a pass).

## 5. Dataset Schema

Each generated file is a JSON array of conversation objects:

```json
{
  "turn": 1,
  "user": "...",
  "assistant": "..."
}
```

Generated `turn` values are renumbered from 1 within each case. Source boundaries are documented in the case allocation table above.
